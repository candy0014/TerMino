# TETR.IO 多人对手版面传输：补充核验与应用

本轮继续核对 [TETR.IO 官方客户端](https://tetr.io/js/tetrio.js) 的多人显示路径，并改进本项目已经存在的完整 / 缩略订阅。重点是减少多人观看时的重复工作，不把远端画面的平滑播放解释为零物理延迟。

## 官方客户端可确认的行为

2026-10-15 重新下载的客户端大小为 2,547,353 字节，SHA-256 为 `b310aaf13ac0d7ee73c87c58abcdec87e1267217e182c10f4c9cb40dc5d73c92`，与之前审阅的版本相同。

新增 [audit_tetrio_multiplayer_views.cjs](../tools/audit_tetrio_multiplayer_views.cjs)，在隔离 VM 中执行原始 scope 和简化版面方法，并核对显示分支。复现：

```sh
curl --fail --location https://tetr.io/js/tetrio.js -o /tmp/tetrio-multiplayer-20261015.js
node tools/audit_tetrio_multiplayer_views.cjs /tmp/tetrio-multiplayer-20261015.js runlogs/tetrio-multiplayer-views-20261015.json
```

脚本拒绝未审阅的客户端哈希。官方包只保存在 `/tmp`，不随项目分发。结果位于 `runlogs/tetrio-multiplayer-views-20261015.json`。

| 显示路径 | 可确认的内容 | 对延迟的意义 |
|---|---|---|
| full / small | 均订阅完整 scope，远端通过带帧号的事件重建 | small 不等于简化版面协议 |
| tiny | 取消完整 scope，接收固定方块、火力、累计收垃圾量、宽高 | 不包含活动块、NEXT、HOLD 或秒表；无需为每块小图持续播放完整游戏 |
| 简化版面打包 | 一个 `game.replay.board` 消息可以包含多个玩家的版面 | 减少大量对手逐条传输的开销；无法由接收方法推出实际批量和发送频率 |
| 裁切 | 导出时去掉上部空行；接收时恢复顶部空白 | 减少固定版面的重复数据 |
| 完整视图已同步 | 忽略 tiny 状态注入 | 两种视觉流不会互相覆盖 |
| tiny → full | scope 请求后仍需完整状态基准；注入状态时调整事件位置 | 请求发出不代表已经恢复同步 |

显示模式受人数、布局和画质影响。默认 FFA 的主观察对象仍为 full；旁边其他玩家达到 9 个时会选 tiny，纯网格达到 9 个玩家时会选 tiny。`alwaystiny` 和最低画质也会触发 tiny。不能概括为“多人房间所有非本地玩家始终只发小图”。

原方法实验还确认：取消 scope 立即发出；重新开启 scope 使用 **300 ms 防抖**，在此期间再次取消会撤销未发请求。这是订阅切换防抖，不是正常动作发送等待。本项目保留即时切换，未照搬这段额外等待。

`f` 为 fire，`g` 为 garbagereceived，均不是时间或帧号。tiny 画面看起来几乎同时变化，不能证明双方逻辑帧完全相等。完整视图的计时和追帧另见 [秒表核验](TETRIO_TIMER_SYNC_20261015.md)。本轮没有真实房间抓包或私有服务端源码，因此不报告 TETR.IO 实战 Hz、流量或端到端延迟。

## 本项目的具体改动

1. **独立采样缩略图。** 提取 `send_mini_board_frame`。视觉轮询中，缩略图采样到期只执行投影发送；完整快照仍由真实状态更新、落块、恢复请求及 500 ms 修复心跳触发。此前同时存在完整和缩略订阅时，采样会进入完整编码路径；保存的落块信息还会反复触发完整快照。
2. **只恢复新切入的完整对象。** relay 比较每位玩家的前后订阅，保留的完整对象不因其他缩略图尺寸变化而重发旧快照。保留的相同缩略订阅也不重置交付序号。新切入完整视图仍立即发缓存基准，并由发送方补充当前校准。
3. **清理不再使用的播放队列。** 隐藏、完整 / 缩略模式切换时清理对应远端时间线。已收到原生缩略流的对象降级后，迟到的完整画面在解码前被过滤；已排入收件箱的视觉包也重新检查兴趣。攻击和回合消息继续独立处理。只支持完整协议的旧发送方仍允许接收完整状态并在本地投影。
4. **复用缩略投影。** relay 为每个发送方缓存最多 4 种请求尺寸。固定版面、尺寸或逻辑几何变化时失效；纯序号和计时心跳复用格子投影，序号和时间仍取最新源帧。修复心跳继续补偿在 relay 缓存中的时间；冻结的计时不前进。换局、取消和离开时释放缓存。

继续使用 `!view-v1` / `!budget-v1` / `!mini-v1` 和原有动作协议。`!mini-v1` 已有游程压缩，上部空白可紧凑表示；WebSocket 已有协商式 TES1 批量封装与未发送视觉状态合并。因此本轮没有为表面上复刻官方结构引入另一层不兼容格式，也没有改变攻击投递语义。原有每批最多 3 个缩略版面的轮转保持不变。

## 对照与验证

混合订阅对照使用真实本地 UDP relay、一个完整观众和一个 12 Hz 缩略观众。测试在 1.1 秒内反复更新固定格子并轮询视觉发送，预置已有落块信息；不是按键到屏幕或公网延迟测试。

| 指标 | 修改前的发送对象文件 | 修改后 |
|---|---:|---:|
| 完整快照数 | 14 | 2 |
| 缩略图数 | 14 | 14 |
| 完整快照字节，按既有统计口径、不含外层房间包 | 2,233 | 261 |

旧路径减少约 86% 的完整快照；此比例仅对应这个混合订阅采样场景，不代表整局总流量减少同样比例。旧实现使用本轮修改前保存的 `board_view.cpp` 和 `multiplayer_channel.cpp` 重新编译，并与相同的其余库和测试夹具链接。日志：`runlogs/multiplayer_views_before_20261015.txt`。

`adaptive_board_view_test` 覆盖混合订阅、旧全量包过滤、攻击保留、重新切回 full、超过缓存容量的连续尺寸切换、新源状态失效、修复心跳的流逝 / 冻结计时及旧发送端回退。`board_view_stagger_test` 增加 32 人参数，验证 31 个对手版面都能交付，并维持每批最多 3 个的节奏。

验证结果：

- Linux 的 14 项网络、房间、布局及同步相关 CTest 全部通过；最终收件队列清理补充后，再次通过 `adaptive_board_view` 和扩展后的 `network_websocket`。后者运行完整的缩略 / 完整视图场景，分别经过旧单消息网关和协商式 TES1 网关。
- 本地 32 人 UDP 房间的 31 个对手版面全部交付，单批最多 3 个，首末批相隔约 156 ms。该测试单独设为 6 Hz 来核验轮转；正常界面超过 16 人时仍按原有预算最高 4 Hz，结果不是公网延迟或 UI 刷新率承诺。
- Windows/Wine 的混合订阅、32 人交付和混合同步检查通过；31 个版面的首末批相隔约 163 ms。最终 Windows 客户端也通过旧网关与 TES1 网关的完整视图场景及既有 WebSocket 集成检查。
- 研究脚本输出可重复，修改官方包后拒绝执行；Python 语法检查和本轮已跟踪文件的差异空白检查通过。
- Linux `build/tetr`、`build/tetr_server`，以及 Windows `build-portable-windows-wine/tetr.exe`、`tetr_server.exe` 均已重新构建。
