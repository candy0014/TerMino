# 公网实时对战：部署、目标与实测（2026-10-15）

> 后续优化、当前部署和最新客户端请见 [2026-10-15 公网传输与绘制优化](PUBLIC_REALTIME_OPTIMIZATION_20261015.md)。本文以下内容为此前部署与测量的历史记录。

本轮以用户明确的公网目标为准：双人对手版面尽量低延迟、平滑呈现；更多玩家时尽量提高可见版面的实时性和帧率；始终优先本地操作。验收使用持续对局数据、版面实际提交和本地输入响应，不以两个秒表读数接近代替同步测量，也不将本地回环结果当作公网表现。

## 从跨洋路径切到东京

tetu 的 VPN 恢复后，原启动器仍显式绑定物理网卡并手工解析隧道端点。运行指标确认四条连接都落在洛杉矶；重启同样的启动方式仍然落在洛杉矶。

先保留原连接，以正常系统路由 / DNS 启动候选 connector，确认其连接东京。随后持久安装 `deploy/termino-cloudflare-vpn.conf` 为用户服务的 `route.conf`，让 `run_cloudflare_direct.py --route system` 使用当前正常工作的 VPN。主服务确认东京连接后停止候选 connector。未修改系统 VPN 节点、全局代理、DNS、路由表或公网域名配置。主服务的注册日志确认协议已为 QUIC，两个有效连接为 NRT12 / NRT14，没有遗留临时候选 connector。

默认 `--route direct` 保留物理出口方式；VPN 不可用时，可在 tetu 本机移除此服务的 route drop-in、执行 `daemon-reload` 并重启隧道，恢复原路径。当前 system 模式依赖 tetu 的 VPN 正常运行。

持续公网 probe 的比较：

| 路径 | 样本 | RTT 中位数 | RTT p95 |
|---|---:|---:|---:|
| 原洛杉矶路径 | 20 | 388.94 ms | 612.87 ms |
| 东京主服务，停止旧连接后 | 30 | 180.92 ms | 183.73 ms |
| 最终 release，16 人测量结束后 | 30 | 183.78 ms | 187.80 ms |

这是完整公网 WSS → 隧道 → gateway → relay → 返回的往返，不是对手动作呈现延迟。日志为 `runlogs/public_probe_before_tunnel_refresh_20261015.json`、`runlogs/public_probe_tokyo_final_20261015.json` 和 `runlogs/public_probe_release_final_20261015.json`。工具：`tools/benchmark_public_probe.py`，不加入房间。

## 客户端和传输策略

- 完整对手使用 120 Hz 动作时间戳和显示调度。轮询与绘制按原有节奏推进，不将每次回调的迟到和处理耗时持续累加到下一帧；严重落后时重新锚定，避免连续补帧挤占输入。
- relay 轮转最后一批只访问实际剩余玩家，不在该批回卷到队首；批次和每块版面的发送节奏保留相位，避免可见人数不是三的倍数时，过早访问又触发限流、漏掉一个更新周期。新增七张小图持续 30 Hz 的回归，逐个检查实际交付数量。
- 新增 `!view-v2` / `!budget-v2`，允许完整视图请求 120 Hz、缩略视图请求最高 60 Hz。未确认 v2 时同时发送兼容 v1 订阅；旧服务端忽略新广告也能工作，旧发送方仍收到最高 12 Hz 的 v1 预算。缩略 payload 仍为 `!mini-v1`。
- 缩略图同时受可见像素预算和总更新预算限制。像素预算为每秒 60,000 格，总更新预算初始为每秒 240 个版面，按实际链路反馈在 60–480 之间调整；分配到每张可见小图时请求 4–60 Hz。隐藏对象不订阅。
- 每 500 ms 复用已有时钟 echo 测量当前真实往返。相对本局最短 RTT 的额外延迟明显增大时，将总更新预算降低四分之一；稳定两秒后，每秒缓慢增加 30。已开始的对局不会因此修改开局时刻。它让快链路继续提高频率，也让拥塞链路优先恢复新鲜画面。
- 完整缩略图可以淘汰该玩家队列中的旧缩略图，并将新图放在已有可靠事件之后。攻击、控制和完整检查点均保留原顺序；动作位姿仍不能跨过这些屏障合并。客户端与 gateway 使用同一策略。
- 本地有待处理动作时，远端工作让出。Windows 的快速检查只检查已排队的控制台事件，不为每张小图重新扫描所有键位。收包与单次解码分别使用 250 微秒预算，应用循环使用 750 微秒预算；普通缩略绘制每次最多四张，按 500 微秒预算逐张让出。预算无法硬中断单次解码、绘制或系统输出。

缩略图仍是固定方块投影，不显示活动块、NEXT 或 HOLD；这是多人小图的数据内容选择。完整视图仍显示活动块及相关信息。

## 测量方法和边界

`tests/windows_multiplayer_latency_benchmark.cpp` 使用实际 Win32 控制台输入、游戏循环、网络客户端及绘制代码。各对手客户端都连接上述公网 URL；没有启动本地 relay。测试双方在同一进程中共用单调时钟，记录发送 API 返回附近的序号和时间，再匹配接收端已经提交到 VT 输出的完整 / 缩略状态，从而不依赖跨机器时钟估计。

本地输入指标是注入独立 Win32 控制台队列到验证 VT 输出的时间。它不包含实体键盘、屏幕刷新或真人感知。运行环境为 Wine，不是原生 Windows Terminal 的物理屏幕测试。完整视图源计划 120 次动作每秒；多人负载持续改变可见底行，计划 60 Hz，实际发送由订阅预算和运行速度决定。有效更新率按各可见对手提交次数计算，再取各对手的中位数。

两端均有 CPU、终端和公网波动，因此调度上限不能当成实际帧率保证；本地输入是否接近离线也以本轮分布衡量，不能宣称所有设备、人数和链路完全零影响。

## 当前公网持续负载结果

以下是当前已部署版本、同一次测量流程的结果。毫秒值保留两位，原始数据没有舍入。双人计划 120 Hz 动作；8 / 16 人时每个源持续改变可见固定方块，而不是仅发送不会影响小图的活动块。

| 场景 | 本地输入→VT p50 / p95 | 对手发送→VT p50 / p95 | 对手有效更新率中位数 | 对局 RTT p50 / p95 |
|---|---:|---:|---:|---:|
| 离线，160 次输入 | 1.07 / 1.37 ms | — | — | — |
| 双人，240 次输入 | 1.08 / 1.56 ms | 218.46 / 234.63 ms | 82.54 Hz | 192.75 / 201.40 ms |
| 8 人，240 次输入 | 1.04 / 1.50 ms | 235.38 / 278.43 ms | 15.94 Hz | 201.25 / 234.47 ms |
| 16 人，准备阶段修复后，240 次输入 | 1.03 / 2.12 ms | 479.66 / 1001.27 ms | 4.18 Hz | 218.09 / 867.10 ms |

双人采集 990 个远端呈现样本，更新间隔 p95 为 24.14 ms；8 人采集 1,331 个样本，每张小图更新间隔的汇总 p95 为 108.95 ms。8 人测量结束时总更新预算已降至 135，说明该链路并未一直保持最高频率。16 人有 745 个远端样本，间隔 p95 为 500.68 ms，总更新预算降到最低 60。该次运行只证明修复后完成了这一轮短时公网负载，不能证明长期稳定或大人数目标已达成。这里的 Hz 是状态实际提交到终端的次数，不是帧循环调用频率。

原始结果位于 `runlogs/public_realtime_20261015/measured_offline_offline.json`、`measured_motion120_motion120.json`、`measured_multi8_multi8.json`、`setup_fixed_multi16_multi16.json`，同前缀保存逐次输入 CSV 和终端轨迹。双人和 8 人数据取自 `public-steady`；最终 `public-setup` 仅修正准备阶段的设置重发，持续对局路径相同。测试代码新增阶段日志不会改变传输策略或负载。

16 人首次最终测量未完成：公网连接在测量前中断，终端记录为 `measured_multi16_terminal.log`。补充阶段日志后再次复现：加入房间和设置交换约 4.5 秒完成，逐人 SetReady 阶段开始积压，后续请求触发 5 秒超时。远程 relay、gateway、主 tunnel 没有重启；gateway 日志出现发送队列积压、心跳超时和 reply queue overflow。修复准备阶段设置重复发送后，16 人在约 9.4 秒内完成准备，随后完成 240 次输入的负载测量；日志为 `setup_fixed_multi16_terminal.log`。这次成功不抹除前两次失败，也不能把本地 32 人功能回归当作公网 32 人性能。

## 验证与当前限制

- 最终 Linux 的 15 项相关回归全部通过，覆盖房间、轮次、倒计时、时钟、兼容订阅、分批和持续转发、混合同步、场景调度、WebSocket/TLS。见 `runlogs/public_release_final_ctest_20261015.txt`。准备阶段修复后的首轮组合中 14 项通过，持续 30 Hz 项目时序不稳定；该项原先同时依赖发送端 30 Hz 采样，改成固定 60 Hz 数据供给以独立验证 relay 的 30 Hz 转发，保留每源 1.1 秒收到 27–35 帧的阈值，连续三次通过后再完成最终组合回归。
- 已对实际公网 URL 执行订阅和时钟功能回归：v2 60 Hz 在半秒收到 29 帧，旧发送方仍为 12 Hz 预算；混合视图 1.1 秒内仅两个完整检查点、14 个小图更新。见 `runlogs/public_live_adaptive_views_20261015.txt`。
- Windows/Wine 的混合同步、32 人准备与分批交付、WebSocket/TLS、分片、可靠事件顺序及兼容订阅验证通过。见 `runlogs/public_windows_hybrid_final_20261015.txt`、`public_windows_stagger32_final_20261015.txt`、`public_windows_websocket_final_20261015.txt`。一次额外的本地 WebSocket 并行尝试争用测试端口，已中止并串行重跑，保留了失败日志；公网服务未受此本地端口争用影响。
- 部署回滚测试三项通过，覆盖成功切换、重启失败回滚、文件校验失败不切换。见 `runlogs/public_deployment_rollback_test_20261015.txt`。
- Linux 和 Windows 客户端、静态 Linux relay 已重新构建。本轮自己的输入 p95 接近离线，但不能据此保证所有机器上完全无影响。

当前进展尚未达到全部目标。双人有效更新率较高，但约 218 ms 的呈现延迟仍然可感知；8 人小图约 16 Hz，16 人约 4 Hz 且 p95 延迟超过 1 秒，都不能称为肉眼无差别的流畅度。公网 RTT 本身约 180–200 ms，靠提高客户端刷新率无法消除这段传输时间。

tetu 未发现全局 IPv6；公网 IPv4、入站端口映射条件仍未确认。补充只读检查中，绑定物理源地址并忽略代理，向三个 HTTPS 出口探测端点的连接均超时；路由查询确认走物理接口及其网关。未取得可核验的物理公网地址，因此无法进一步验证 UDP 3000 入站；这些超时不能证明不存在公网 IP。记录为 `runlogs/public_physical_egress_probe_20261015.json`、`public_physical_egress_fallback_20261015.json`。用户目前不确定是否有另一台可直连公网服务器。单独忽略本机环境代理的十次探测，RTT 中位数为 192.51 ms、p95 为 200.94 ms，没有优于现有东京隧道；没有据此更改客户端全局代理设置。若要进一步显著降低延迟，需要可验证的近端直连公网入口作对照，现有 Tokyo connector 不能等同于 relay 本体已搬到东京云服务器。
