# TETR.IO 自己与对手的秒表是否真正同步（2026-10-15）

结论：**完整版面的秒表来自各棋盘自己的逻辑帧进度。带毫秒的读数接近，确实说明这个客户端中，本地模拟与对手重建模拟的时间进度接近。仅凭这些读数，不能证明对手电脑上的最新状态也已无延迟地到达。** 如果只显示整秒，连 100ms 或更大的差距都可能被隐藏。

这次查到的实现并不是统一给所有棋盘填入同一个公共时间。需要特别区分双人或多人中的完整版面，以及 tiny 缩略版面。

## 秒表究竟读取什么

`UpdateTimers()` 的正常运行逻辑可概括为：

```text
显示经过时间（毫秒） = (本棋盘 esm.frame − 本棋盘 time.frameoffset) × 1000 / 60
```

`time.zero` 为真时显示零，`time.locked` 时停止更新。普通未重置的对局中 frameoffset 默认为零；某些自定义规则、复活或重置路径会修改它，不能跨这些情况直接比较帧号。

`ctm.UpdateCounter` 将结果写到**这个棋盘自己的** counter 元素。它没有读取另一名玩家的计时，也没有从全局比赛秒表复制数值。

虽然 `StartStopwatch()` 保存过 `performance.now()`，但上述显示公式不使用这个起始值。显示出三位小数也不代表游戏时间以 1ms 为步长：常规秒表按 60Hz 逻辑帧前进，一帧约 16.667ms，再四舍五入成三位毫秒。`GetGameTime()` API 另包含 subframe，不能与面板显示混为一谈。

## 为什么两块完整版面通常接近

1. **逻辑时间有共同尺度。** 每个棋盘都使用 60Hz 逻辑帧；同一客户端的多人管理器在开始流程中启动已挂接的本地和远端棋盘，不靠持续传输时间字符串来驱动秒表。这不能单独证明不同电脑的实际开局时刻完全一致。
2. **远端按帧号重建。** `game.replay` 给出事件及 provisioned 边界，远端 socket 事件源按对应帧处理。空闲、重力、消行等模拟可在已获得的时间范围内连续运行；不是每次等一张完整棋盘快照才动一次。
3. **播放循环主动减少积压。** 可用帧超过当前播放位置 60 帧时，原循环会递归追加更新，快速压缩较大积压。另有依据 `GetBehindness()` 的额外帧处理，用于较缓和的追赶。
4. **本地继续响应输入。** keyboard 事件源不需要远端 provision；socket 事件源不能越过已获得的边界。网络恶化时可以表现为对手画面和秒表落后，本地照常运行。

这些是本轮从客户端代码及原方法实验可以确认的机制。真实链路的发送批次、服务器处理和抖动仍会影响差距；代码没有给出“正常网络下一定小于某个毫秒数”的保证。

## 原方法实验结果

以下均是人为提供帧号和数据的合成情景，**不是实战延迟统计**。

| 情景 | 本地显示 | 远端显示 / 行为 |
|---|---|---|
| 本地第 635 帧，远端第 629 帧，带毫秒 | `0:10.583` | `0:10.483`，相差 100ms |
| 同样两组帧号，只显示整秒 | `0:10` | `0:10`，差距不可见 |
| 只将墙钟推进 5 秒，不推进远端模拟 | — | 秒表仍为 `0:10.483` |
| 停止提供后续远端帧，双方各请求 60 次逻辑更新 | 从 `0:10.583` 到 `0:11.583` | 停留在 `0:10.483` |
| 远端第 0 帧，一次提供到第 120 帧，再请求一次循环更新 | — | 原循环实际前进 60 帧；追赶不等于一次消除所有缓冲 |
| 模拟较缓和积压，连续请求 10 次更新 | — | 实际前进 12 帧，验证额外追帧 |
| 相同第 629 帧，分别调用 tiny / full 的渲染方法 | — | tiny 不更新秒表，full 更新为 `0:10.483` |

另验证了锁定后的时间不再变化，以及 frameoffset 和 subframe 对显示/API 的不同作用。

## 双人、多人，以及观战/回放的区别

- **实时双人完整版面**：对手秒表反映本机重建的远端进度。若毫秒差距只有一两帧，而且双方计时基准一致，可以说显示端的两套模拟在约一两帧的范围内接近；本轮没有实测用户所见场景是否满足这些条件。
- **实时多人中的 full / small 版面**：沿用相同计时逻辑。是否传完整事件由 scope 订阅控制，不能因在同一房间就假设所有玩家始终用相同详细度同步。
- **tiny 缩略版面**：绘制路径跳过常规 `UpdateTimers()`，并通过简化版面更新。不能将完整棋盘秒表的结论推广为“所有缩略图都已逐帧同步”。
- **观战**：看到的是多个远端重建实例。两个显示时间接近，仍可能是两个实例都落后于实际玩家。
- **已保存回放**：事件已经可用，播放器可以控制各棋盘进度；回放中时间整齐不能用来测原对局的实时网络延迟。

## 对“几乎完全同步”的准确判断

可以区分三层：

| 判断 | 仅凭面板时间能否确认 |
|---|---|
| 两个显示数值接近 | 可以；需确认是否显示毫秒 |
| 本机两个完整版面的逻辑时间接近 | 在计时未锁定、未重置且基准可比时，可以近似判断 |
| 对手电脑此刻的最新棋盘状态已经到达本机 | 不可以；还缺对手实时帧号、发送/接收时刻及开局/时钟基准 |

在明确相同时间原点、固定 60Hz、正常持续运行的前提下，显示差值可作为**本机可见的远端进度差**的近似指标。不能把它直接等同于 RTT，或忽略两端开局偏差、发送批处理、远端缓冲和显示刷新造成的误差。

要给出严格实测结论，需要关联对手产生的事件/状态序号，记录对手实际产生时刻、本机接收和绘制时刻，并对齐双机时钟及其误差。仅把两个数字改成相同不能满足这个目标。

对本项目最有价值的迁移点是：区分比赛经过时间、远端已确认/已播放进度，以及远端状态年龄；让观测能揭示积压，再调整播放缓冲和追赶策略。当前本项目的远端计时还会依据样本继续外推，见[多人说明](MULTIPLAYER_ROOMS.md)，与本轮确认的 TETR.IO 按模拟帧显示存在区别，不能拿两者的秒表差距直接做网络性能排名。
