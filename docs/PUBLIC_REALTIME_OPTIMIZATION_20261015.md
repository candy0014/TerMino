## 改动

1. relay 将同一轮调度中已经就绪的最多三张小图打包为 TES1 UDP 包，网关一次解包入队、一次 WebSocket 转发，不加凑批定时器。只对使用正确连接 token 声明能力的网关端点启用；普通 UDP、旧网关、未协商 TES1 的 WebSocket 保留单包。打包后的 UDP 数据不超过 65,507 字节，必要时分包。
2. 已协商 TES1 的可靠连接不再重复发送语义完全相同的无请求编号房间名单。只忽略心跳生成的不同 revision 数字；角色、准备、成员、房间实例、规则和对局阶段变化仍保留，带请求编号的回复、心跳 pong、离房通知也保留。每次广播只构建一次成员列表。网关只有在前一状态成功入队后才记住它；断线后重新取得当前状态。
3. 自适应小图预算使用最近三次真实 echo RTT 的中位数，避免单次尖峰导致长期低帧率；两次高延迟仍及时降频。若单次 RTT 超过本局最短 RTT 的两倍且额外延迟超过 150 毫秒，则立即按延迟程度更快降低预算，避免等待多个秒级积压样本。总预算范围仍为 60–480，稳定两秒后渐增，不改变已开始对局的时钟。第一轮曾使用三次样本的最小值，16 人测试仍有积压，最终改成中位数，保留中间结果供对照。
4. 小图发送按原有时间相位采样，避免每次回调迟到都重置下一次采样时间。传输队列只校验小图头部、时间戳和所有颜色/游程，不构建临时格子数组；显示端需要时才解码。房间、设置和订阅解析先检查协议前缀，避免把视觉包分割为无关字段。
5. 终端将同一行连续同色的变化格子合并输出。已收到的新小图在下一次远端绘制机会立即处理，跳过未变化的玩家，不再按网络请求帧率二次等待。继续轮转，每次最多四张，使用 500 微秒预算并检查本地输入；旧发送方的完整协议投影保留原采样节奏。预算不能硬中断单张图或系统写入。

完整对手仍使用时间戳动作和完整校准；小图仍为固定方块投影。这轮没有通过丢攻击、控制或完整检查点提高帧率。

## 公网测量

所有性能案例都连接真实公网入口，未启动本地 relay。每次 240 次 Win32 输入，约 12 秒持续负载，Wine 实际游戏循环和 VT 输出核验。双方测试端共用单调时钟，匹配发送序号与已提交的远端状态；不依赖两台设备秒表看起来一致。有效 Hz 为每个可见对手实际提交到 VT 的次数，再取中位数。输入指标不包含实体键盘、显示器刷新或原生 Windows Terminal 的像素呈现。

双人源计划 120 Hz 动作；8 / 16 人不断改变可见固定格子，发送频率受实际订阅预算约束。额外做了改前/改后可执行文件交替测量，所有中间结果保存在 `runlogs/public_optimization_20261015/`，未删除不利结果。该公网路径的空闲 RTT 在约 180–390 毫秒之间变动，16 人负载还可能出现秒级排队；不同场次的延迟差不能全部归因于程序优化。
