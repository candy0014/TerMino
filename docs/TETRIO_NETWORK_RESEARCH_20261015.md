# TETR.IO 房间多人 / 排位双人网络考察（2026-10-15）

结论：适合迁移的是**本地独立运行、带时间的增量流、完整/缩略订阅、攻击因果确认、链路选择**这一组机制。本项目已有其中大部分。现阶段应沿用现有兼容协议，先测出链路、排队和绘制各自的延迟，再做定向优化；暂不把整个联机改成纯输入回放或全局 rollback。

以下项目现状记录调研时的基线。后续已实施的数据就绪收发、自适应缓冲和追赶机制，见[低延迟实现与验证](LOW_LATENCY_NETWORK_20261015.md)。

TETR.IO 的“几乎没有延迟”首先是本地操作不等远端；对手动作、攻击到达和最终判定仍有传输及处理时间。这几种延迟必须分别测量。

自己与对手的时间读数为何接近，另见[秒表同步专项核验](TETRIO_TIMER_SYNC_20261015.md)：完整版面时间来自各自的逻辑帧进度，包含原始计时/播放方法的实验结果。

## 1. 传输层：Ribbon WebSocket 与区域代理

官方客户端的 Ribbon 使用 `new WebSocket(this._uri,this._spoolid)`；默认经二进制编码器处理消息。回放包使用专门的位编码结构，带 gameid、provisioned 和事件数组，不是逐次发送整块棋盘的 JSON。

可确认的连接过程为：获取 `/api/server/ribbon` 的 endpoint / spool 信息，选择区域 spool，建立 WSS；失败时存在回退与恢复路径。客户端还会定期重新评估 spool，并在满足改善条件时切换。开发者也明确将 spool 描述为“regional WebSocket proxy”，见[官方说明](https://blog.osk.sh/post.php?p=688966e719b753.49360626)。

因此，正常游戏链路应理解为：客户端 → 区域 WebSocket 代理 → 服务端 → 对端代理 → 对端客户端。所核对的客户端主对战路径没有显示房间走 UDP、排位另走 WebRTC/P2P 的分流。服务端内部采用什么传输，不能由浏览器 WSS 推断。

Ribbon 还为带消息 ID 标志的消息保存发送缓存，通过接收序号释放，在恢复会话时补发。这是会话恢复机制，不能解释成 WebSocket 平时靠 UDP 式重传运行。

**容易误读的常量**：当前包里 `_BATCH_TIMEOUT=25` 仅出现一次，即声明。实际 `_send_internal` 直接调用 WebSocket send。不能据此声称 Ribbon 固定等 25ms 才发包，也不能把本项目的 8ms 事件合并窗口称为官方 Ribbon 的原样移植。

## 2. 房间多人和排位双人的共同基础

房间及 Tetra League 界面复用同一多人管理器；本地玩家创建 keyboard 事件源，对手创建 socket 事件源。客户端没有表现出两套截然不同的底层对战传输。

| 内容 | 客户端可确认的机制 | 含义 |
|---|---|---|
| 本地输入 | keyboard 事件源立即进入自己的游戏循环 | 不等对手输入或网络确认 |
| 完整对手版面 | `game.replay` 携带帧号事件，socket 事件源在原引擎重建 | 持续发送全部棋盘不是必要条件 |
| 更新完整画面 | full / small 显示触发 scope 订阅 | 只为需要完整展示的对象维持相应数据 |
| 多人缩略版面 | tiny 取消完整 scope，`game.replay.board` 注入简化固定版面 | 降低大量对手的流量和模拟负担 |
| 切换观察对象 | `game.replay.state` 注入完整状态并调整事件帧位置 | 重新订阅后恢复正确基准 |
| 攻击及交互 | 本地接收 `game.replay.ige`，包含交互确认 | 与远端完整画面的播放分工不同 |

双人通常需要对手完整版面；多人更多使用缩略版面。这是订阅和展示需求的差异。不能从共享客户端代码推出两种模式的服务端部署、发送频率、裁判负载完全一致。

完整事件流包括 keydown / keyup 的帧号与 subframe，以及交互、状态等事件。它与本项目现有的“移动结果姿态 + 关键帧”不同：前者依赖一致引擎重演，后者直接传输已经解析的位姿。

## 3. 本地无等待与远端播放并存

事件源的推进条件是：本地键盘始终可推进；socket / pipe 只能推进到已经 provision 的范围。隔离执行原方法得到：

- 没有任何远端数据，本地仍可推进。
- 远端没有 provision 时不能推进。
- 其他 gameid 的数据被忽略。
- provision 到 10 时，远端恰好能前进 10 帧，然后停止。
- 远端积压超过 60 帧时触发落后检测；引擎另有追帧与较小幅度的播放速度修正。

这支持“各自独立运行、远端有序重建”的解释，不支持将其简单归类为双方逐帧互等的 lockstep。在审阅的主要路径中，也没有证据表明本地每次输入都依赖 GGPO 式全局回滚预测。

发送端同样有缓冲。Replay 使用 latency mode、provisionSpeed、事件队列与显式 flush。**档位表不是实际发包间隔承诺**。本轮直接调用原方法，在 120 次 AdvanceFrame 内每 6 帧插入一次 keydown，结果为：

| 设置 | 第一次发送发生在第几次 AdvanceFrame | 120 帧内批次数 |
|---|---:|---:|
| zero / low | 15 | 8 |
| medium / high / xhigh | 50 | 2 |
| 任意档位，每次事件后显式请求 flush | 事件后的第一次 AdvanceFrame | 20 |

以上是**合成调用实验**，不是实战发包率。真实游戏还有 start、full、end、交互等触发条件和服务端下发参数。客户端的 interaction / action 分支可请求下一帧 flush，但这里的 action 不能等同于每次横移或硬降。不能看到 zero 档位表中有 2，就认定实战必然每两帧发送。

引擎按 60Hz 逻辑帧组织事件并保留 subframe；因此帧批处理还会带来时间量化。客户端局部立即响应与网络事件成批发送完全可以同时成立。

## 4. 攻击：因果抵消与画面同步

客户端对 zero / consistent passthrough 维护按目标区分的待确认攻击。交互里带 `iid` 与 `ackiid`；收到对方攻击时，用对方已确认的边界判断哪些自己发出的攻击还能参与在途抵消。

它解决的是双方几乎同时出手、尚未看见对方攻击时的因果一致性，不会缩短物理传输时间。[官方更新记录](https://tetr.io/about/patchnotes/)在 2023-04-12 介绍 zero passthrough，2023-05-14 将其设为默认；更新记录也提示网络延迟下仍可能出现少量穿透。当前审阅包的引擎默认值仍为 zero，但具体排位对局参数需真实会话另行核实。

另一个不能遗漏的细节：`interaction_confirm`、`kev`、`targeted` 在满足条件时，可以等待被观察对象播放到指定帧，超时回退为 4 秒。并非所有攻击交互都在数据到达的瞬间完成全部展示/处理。不能因此让本项目的本地按键或可靠投递确认等待远端绘制。

## 5. 与本项目逐项对照

| 机制 | 本项目现状 | 建议 |
|---|---|---|
| 本地不等待网络 | 本地逻辑先执行；远端单独维护状态 | 保留；测网络轮询、解码和输出是否挤占输入线程 |
| 带时间的增量传输 | 120Hz 动作时间戳、绝对结果位姿、版本和指纹 | 保留，适合自定义规则、地图与个人手感 |
| 完整/缩略订阅 | `!view-v1` / `!budget-v1` / `!mini-v1`，按可见对象与尺寸分发 | 方向一致，优先验证满房和切换对象时的恢复 |
| 可靠攻击 | 存储确认、目标投递序号、去重和补发 | 保留独立时序，继续验证在途抵消和改目标边界 |
| 短窗口合并 | 已有协商式 `termino.events.v1`，视觉更新目标窗口 8ms | 属于本项目自己的传输优化；不要套用到原始输入事件 |
| 远端缓冲 | 当前固定 35ms 时间线，远端完整显示最多 60Hz | 稳定低抖动链路可试更小或自适应缓冲，先做对照实验 |
| 远端追帧 | 绝对姿态修复、快照修复、超过一定偏差重新锚定 | 验证突发积压的恢复；不能把有效落块、攻击当视觉旧帧丢掉 |
| 区域路径选择 | 当前配置单个服务器地址，经网关/隧道接入 | 是与 TETR.IO 的明显差异；先对照直连路径与现有公网路径 |
| 服务端验证 gameplay | 当前 relay 路由、去重、控制生命周期；不是完整游戏裁判 | 若未来做可信排位，需要另加验证，换传输协议不足以实现 |

对应代码：

- [multiplayer_channel.cpp](../src/network/multiplayer_channel.cpp)：位姿、关键帧和初次攻击发送。
- [hybrid_sync.cpp](../src/network/hybrid_sync.cpp)、[hybrid_sync.h](../include/tetr/network/hybrid_sync.h)：远端时间线和 35ms 缓冲。
- [multiplayer_client.cpp](../src/network/multiplayer_client.cpp)、[multiplayer_relay.cpp](../src/network/multiplayer_relay.cpp)：订阅、攻击确认、补发与远端消息。
- [websocket_socket.cpp](../src/network/websocket_socket.cpp)、[event_stream.h](../include/tetr/network/event_stream.h)、[event_stream.py](../tools/event_stream.py)：WebSocket 轮询和视觉队列。
- [frame_pump.cpp](../src/network/frame_pump.cpp)、[network_services.cpp](../src/network/network_services.cpp)：游戏线程处理网络的时间预算。

尤其需要区分：现有事件合并可以覆盖**相同版面版本的绝对结果位姿**，因为后一个结果足以定位。纯输入流里的 keydown / keyup 不能这样覆盖，否则会改变 DAS、松键、Hold 与锁定的结果。沿用 TES1 外壳并不代表能沿用其视觉消息的丢弃策略。

## 6. 推荐的落地次序

### 第一阶段：先分清实际延迟来自哪里

建立关联到 epoch / player / sequence 的诊断记录，分别测：本地输入到模型提交、本地输出提交、发送排队、网关排队、relay 接收/转发、接收排队、远端模型应用和远端输出提交。记录 p50 / p95 / p99、最长停顿和队列年龄，不能只记平均 ping 或队列条数。

同机双客户端可直接用同一单调时钟测端到端年龄；跨机器必须记录时钟校准误差，未经校准不把两端时间戳相减当作单向延迟。VT 输出提交、终端格子更新与屏幕像素显示也分别标注。

完整测试矩阵建议为：同机 UDP、同机 WebSocket、可用时的直连 WSS、现有公网 WSS；各跑 2 / 8 / 16 / 32 人，加入双向延迟、抖动、突发暂停，以及 UDP 段丢包。对 WebSocket/TCP 的包丢失观察其重传和队头阻塞，不将其模拟成可以任意丢弃完整 WebSocket 消息的传输。

判断依据：网络延迟升高时，本地输入到输出的分布应接近同负载离线基线；远端更新不能无限积压，停顿恢复后应回到当前状态；可靠攻击不得漏、重或跨局。具体数值门槛由第一轮基线确定，不能拿本轮静态调研充当性能达标证明。

### 第二阶段：优化现有同步和接入路径

1. 比较公网路径，定位隧道/代理额外绕路，再决定是否增加可选择的直连 WSS 或区域接入点。选择应依据持续 RTT、抖动、失败率和队列年龄；一个更近的代理不保证整条路线更快。
2. 对稳定链路试验远端 8–16ms 与当前 35ms 缓冲；抖动时适当回升。测试重排、丢失关键帧及切换主目标，不直接把默认值改成零。
3. 检查网络处理的总时间预算。当前若干限制是单次调用预算，frame pump 会继续消费；仍需实测持续高负载是否推迟下一次本地输入。
4. 持续保留攻击/控制的立即触发、顺序边界与可靠性。视觉合并只能减少尚未提交到 TCP 的积压，不能越过已在 TCP 中传输的数据。

在稳定及时到达的阶段，本项目自身还可能引入发送端约 8ms 合并、网关约 8ms 合并、35ms 时间线与最多约一帧的 60Hz 显示等待。它们是不同阶段的设计量，**不是严格端到端上界，也不是每包都会完整相加**；调度、突发和时间线重锚定均会改变实际值。降低其中几毫秒不能补偿数百毫秒的绕路或积压。

### 第三阶段：仅在收益明确时试验纯输入重建

可先对单一规则、双人完整版面增加可协商的输入回放能力；继续保留现有结果位姿/关键帧回退。握手需要引擎版本、规则/配置指纹、每名玩家的随机种子和初始化状态。

检查点必须覆盖场地、活动块、块序、Hold、随机数状态、按住的键、DAS/ARR、重力/锁定/进块/消行计时、垃圾队列和攻击因果边界。BOT 应记录实际执行的动作和时间；不同 BOT 或不同机器的搜索结果不能自行再计算来替代。

当前项目大量玩法使用 Duration 与事件到期时间，还包含按落块推进的模拟时间和自定义规则。直接接入 TETR.IO 的 60Hz/subframe 数据格式不会自动得到确定性。应先用同一事件流验证本地与远端检查点一致，再比较完整双人画面的带宽和 CPU；多人缩略图继续使用投影更合适。

这是一项独立实验，收益尚未验证。本轮不改变现有线上协议、35ms 默认缓冲、服务器地址或部署。

## 本轮验证结果

- 离线核验脚本语法检查通过；固定哈希的官方客户端通过全部静态定位和原方法行为断言。
- 核验输出重复运行一致；未知客户端哈希拒绝执行。
- 本轮新增研究工具、结果和调研文档，没有修改运行时网络逻辑。因此不以旧构建目录中的 CTest 结果作为本轮源码验证，也不声称已经降低实际联机延迟。
